## 公司 PRD 标准结构（8 章）

```
1. 文档信息          作者、版本、评审人、状态
2. 背景与目标        业务背景、痛点、目标、不在范围
3. 用户与场景        用户画像、典型场景、用户旅程
4. 需求清单          功能列表 + 优先级 (P0/P1/P2)
5. 详细需求          逐条需求详细设计
6. 流程与交互        业务流程图、状态机、关键交互
7. 接口与数据        前后端接口、数据结构、依赖
8. 非功能与上线      性能、安全、监控、灰度、回滚
```

## 2. 背景与目标

### 2.1 业务背景
一句话说清楚：**为什么要做这个需求？**

例：
> 当前 hytech-cpa 系统中，代理在出金申请时无法实时看到自己当前的可用余额，需要切换到"余额查询"页才能看到。
> 数据显示有 23% 的代理因不知道余额额度而提交超额申请，导致重复操作和投诉率上升 15%。

### 2.2 目标

**业务目标**（可衡量）：
- 减少出金超额申请 → 目标降低到 5% 以下
- 投诉率下降 → 目标恢复到 10% 以下

**用户目标**：
- 代理在出金页面一眼看到当前可用余额
- 减少跳转操作

**技术/产品目标**：
- 不引入新的服务依赖
- 接口响应时间 < 200ms

### 2.3 不在本期范围（Non-Goals）
- ❌ 不调整出金申请的核心流程
- ❌ 不修改余额计算规则
- ❌ 不涉及历史余额查询页面

---

## 3. 用户与场景

### 3.1 目标用户

**主要用户**：代理 IB（hytech-cpa client 端登录的用户）
- 角色画像：xx 公司外部代理，每月平均申请出金 1.8 次
- 痛点：申请时不知道可用余额，常因超额被拒绝

**次要用户**：运营审批员
- 影响：减少超额申请后审批量下降，可专注更高价值审核

### 3.2 典型场景

**场景 1（主场景）**：代理日常出金
```
张代理周二想申请提现 $1000：
  → 登录 client 端
  → 进入"出金申请"页面
  → 一眼看到顶部显示"当前可用余额：$1,235.50"  ← 新增
  → 输入 $1000，提交
  → 提示"提交成功，等待审批"
```

**场景 2（边界场景）**：代理刚好金额到位但有锁定中
```
李代理：可用 $500，锁定 $300：
  → 进入"出金申请"页面
  → 顶部显示"当前可用余额：$500.00（另有 $300 锁定中）"
  → 李代理理解只能申请 $500
```

## 5. 详细需求

### REQ-1 · 出金页顶部展示可用余额

**描述**：在 client 端"出金申请"页（路径：`/payment/apply`）顶部新增一个余额卡片。

**界面**：
```
┌─────────────────────────────────────────┐
│  当前可用余额                            │
│  ┌────────────────────────────────────┐ │
│  │  $1,235.50 USD          [刷新]    │ │
│  │  另有 $300.00 锁定中               │ │
│  └────────────────────────────────────┘ │
│                                          │
│  申请提现金额：[       ] USD             │
└─────────────────────────────────────────┘
```

**字段定义**：
| 字段 | 类型 | 来源 |
|---|---|---|
| 可用余额 | BigDecimal | `AccountBalanceEntity.availableBalance` |
| 锁定余额 | BigDecimal | `AccountBalanceEntity.lockedBalance` |
| 货币 | String | `AccountBalanceEntity.currency` |
| 刷新时间 | LocalDateTime | 前端记录 |

**业务规则**：
1. 用户进入页面立即查询并展示
2. 锁定余额 = 0 时，不显示"另有 xx 锁定中"
3. 余额为 0 时，"申请提现金额"输入框置灰，提示"暂无可用余额"

**异常处理**：
- 接口失败：显示"-- USD"，下方提示"加载失败，请刷新"
- 网络慢：3 秒未返回时显示骨架屏

### REQ-4 · 输入金额超额时实时提示

**描述**：当用户输入的金额 > 可用余额时，输入框下方红字提示。

**示例**：
```
申请提现金额：[ 1500 ] USD

## 6. 流程与交互

### 6.1 业务流程

```
用户进入页面 ─→ 调用 GET /bsn/payment/balance
                      ↓
              ┌──────────────────┐
              │ 余额 > 0 ?       │
              └──────────────────┘
                ↓ 是           ↓ 否
        显示余额 + 输入框    显示"暂无可用余额"
                ↓
        用户输入金额
                ↓
        前端校验：≤ 可用余额？
                ↓ 是           ↓ 否
        启用提交按钮      显示超额提示，按钮置灰
                ↓
        点击提交 → POST /bsn/payment/apply
                ↓
        显示提交结果（成功 / 失败）
```

### 6.2 关键交互细节

- 余额数字使用千分位分隔（$1,235.50）
- 货币代码大写（USD / EUR / JPY）
- 按钮 hover、loading、disabled 三态明确

## 7. 接口与数据

### 7.1 接口设计

#### GET /bsn/payment/balance

**用途**：查询当前登录代理的可用 / 锁定余额

**入参**：无（从 token 取 userId / cpaAccount）

**出参**：
```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "availableBalance": "1235.50",
    "lockedBalance": "300.00",
    "currency": "USD",
    "lastUpdated": "2026-06-01T12:30:45+08:00"
  }
}
```

**鉴权**：需要 client 端 token

**性能要求**：P99 < 200ms

**降级**：返回旧缓存或 503

### 7.2 数据来源

- 主表：`tb_p_c_account_balance`
- 关联：`AccountBalanceEntity.account = currentUser.cpaAccount`

### 7.3 依赖系统

| 系统 | 用途 |
|---|---|
| hytech-cpa-client（本系统）| client 端接口 |
| hytech-cpa-core-backend | 余额数据 |

## 8. 非功能与上线

### 8.1 性能
- 接口 P99 < 200ms
- 余额查询 QPS 峰值 100/s（代理总数 2000）

### 8.2 安全
- token 必须有效
- 只能查自己的余额（业务层鉴权）
- 敏感金额日志脱敏

### 8.3 可观测
- 接口埋点：QPS、RT、错误率
- 业务监控：余额查询失败率告警阈值 > 1%
- 失败发飞书告警 → 「Balance 查询失败」群

### 8.4 灰度与回滚
- 灰度策略：先 5% 代理 → 50% → 100%（按 cpaAccount 哈希）
- 回滚方案：前端开关一键回退到旧版页面

### 8.5 测试要求
- 单测覆盖率 ≥ 70%
- 接口自动化用例 ≥ 8 个
- 性能压测：模拟 200 QPS 持续 5 分钟

### 8.6 上线计划

| 阶段 | 日期 | 内容 |
|---|---|---|
| 需求评审 | 2026-06-01 | PRD 评审通过 |
| 技术评审 | 2026-06-03 | 技术方案评审 |
| 开发完成 | 2026-06-10 | 提测 |
| 测试通过 | 2026-06-15 | UAT 完成 |
| 灰度上线 | 2026-06-18 | 5% 代理 |
| 全量上线 | 2026-06-22 | 100% |

### 8.7 监控指标

| 指标 | 目标值 |

## 撰写 PRD 的 5 大原则

### 原则 1 · 数字优先，少用形容词

❌ 「**提升**用户体验」「**加快**响应」「**很多**代理反馈」
✅ 「将出金申请超额率从 23% 降至 5%」「响应时间从 800ms 降至 200ms」「160/700 代理反馈」

### 原则 2 · 反例 + 异常分支必写

❌ 只写"用户正常操作流程"
✅ 必须写：输入非法、网络失败、并发提交、超时、空数据怎么显示

### 原则 3 · Non-Goals 必写

不写明"不做什么"会被研发反复追问、产品自己也会越界。

### 原则 4 · 接口出入参用 JSON 示例

抽象描述（"返回余额对象"）= 没说。给具体 JSON = 一目了然。

### 原则 5 · 优先级标记 P0/P1/P2

P0 一定要做，P1 排不进可以下迭代，P2 老板想砍随便砍。

## PRD 自检 Checklist

写完发评审前自查：

```
背景章
□ 业务背景一句话讲清
□ 有可量化的目标
□ 写了 Non-Goals

用户场景章
□ 至少 1 个主场景 + 1 个边界场景
□ 用真实角色名（"张代理"而不是"用户A"）

需求清单章
□ 每条需求有 ID、优先级、负责人
□ 没把 P0 写到 5 条以上（多说明范围太大）

详细需求章
□ 每条需求有：界面 / 字段 / 业务规则 / 异常处理
□ 字段类型、来源、约束明确

流程章
□ 主流程有图（ASCII / 流程图）
□ 状态机有图

接口章
□ 出入参 JSON 示例
□ 鉴权要求
□ 性能要求
□ 降级方案

非功能章
□ 性能、安全、监控、灰度、回滚都有
□ 测试覆盖率要求
□ 上线计划带时间节点
□ 监控指标可量化
```

## 反例：常见的 PRD 错误

| 错误 | 后果 | 改正 |
|---|---|---|
| "支持批量操作" | 研发追问：批量上限？性能要求？事务边界？ | 明确：单批 ≤ 1000 条，10 秒内完成，部分失败不回滚 |
| "异常时提示用户" | 测试追问：提示文案？提示级别？错误码？ | 给出具体文案 + 错误码 + UI 样式 |
| 没写优先级 | 项目排期混乱 | P0/P1/P2 明确 |
| 没写 Non-Goals | 研发越做越多，工期延期 | 写清不做什么 |
| 拍脑袋数字 | 评审时被业务质疑 | 数据来源标清楚 |
| 缺降级方案 | 上线踩坑 | 必须写降级 + 回滚 |
| 无监控指标 | 上线后效果不可衡量 | 必须给出可量化指标 |
