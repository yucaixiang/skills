# incident-response · 重大故障应急流程

> P0/P1 重大故障应急的标准化流程。让"乱军"变"组织"，从混乱中拿回控制权。

---

## When to Activate

- 发生 P0/P1 故障，需要协调多团队
- 需要任命 Incident Commander (IC)
- 用户说"严重故障"、"全站不可用"、"资金问题"
- 与 `oncall-trading` Skill 配合：值班发现故障 → 升级 → 本 Skill 接管
- 需要对外沟通（业务方 / 老板 / 客户）

---

## 故障等级与响应

| 等级 | 定义 | IC 角色 | 响应时间 | 目标恢复时间 |
|---|---|---|---|---|
| **P0** | 全站不可用 / 资金错误 / 监管事件 | Tech Lead 或更高 | 5 分钟 | 30 分钟 |
| **P1** | 核心功能不可用 / 单品牌故障 | 资深研发 | 15 分钟 | 1 小时 |
| **P2** | 非核心异常 / 少量数据问题 | 当班值班 | 30 分钟 | 4 小时 |
| **P3** | 体验问题 | 值班记录 | 2 小时 | 24 小时 |

> P2/P3 走 `oncall-trading` 即可。本 Skill 主要面向 P0/P1。

---

## 角色矩阵（P0/P1 必备）

| 角色 | 职责 | 谁来当 |
|---|---|---|
| **IC** Incident Commander | 总指挥，最终决策 | Tech Lead / 资深研发 |
| **Comms Lead** | 对外沟通，发对内/对外通知 | 产品 / TL 兼任 |
| **Ops Lead** | 操作执行（重启 / 回滚 / 限流） | 当班值班 / SRE |
| **Investigator** | 排查 / 找根因 | 业务模块 Owner |
| **Scribe** 记录员 | 记录时间线、决策、操作 | 任何在场的人 |

⚠️ **每个角色必须有人，不能空缺**。一个人可以兼多个角色，但角色不能没人。

---

## 5 阶段应急流程

```
┌─────────────────────────────────────────────────────────────┐
│  阶段 1 · 发现       告警/反馈/监控                          │
│  阶段 2 · 响应       IC 接手、拉群、定级                     │
│  阶段 3 · 控制       止血优先（隔离/降级/限流）              │
│  阶段 4 · 恢复       根因修复、全量验证                      │
│  阶段 5 · 复盘       24h 内产出故障报告                      │
└─────────────────────────────────────────────────────────────┘
```

---

## 阶段 1 · 发现（0-5 分钟）

### 触发方式
- 飞书告警（`hytech-cpa-alert` 自动推送）
- 监控大盘告警（Grafana）
- 业务方 / 客户反馈
- 内部同事发现

### 第一响应人动作
1. 在飞书告警群 acknowledge：「@当班 已接手」
2. 快速判断等级（按上表）
3. **如果是 P0/P1，立即升级**：触发本 Skill 流程

⚠️ **重要**：宁可错升级，不要漏升级。事后发现是 P2 → 撤销很简单；事后发现是 P0 但当成 P2 → 损失不可逆。

---

## 阶段 2 · 响应（5-15 分钟）

### Action 1 · 任命 IC

```bash
lark-cli im send --chat "#技术值班群" \
  --content "P0 故障：[标题]
@xiaodong.wang 担任 IC，负责本次故障指挥。"
```

### Action 2 · 拉战时群

```bash
lark-cli im create-chat \
  --name "#P0-[故障简称]-MMDD-HHmm" \
  --members "@IC @TL @业务Owner @SRE @产品 @合规（如涉及）"
```

### Action 3 · 定级 + 初步通报

群内首条消息标准格式：

```
🔴 P0 故障应急启动

【时间】2026-05-31 02:00
【现象】佣金计算停止，5 分钟无新记录生成
【影响】全部代理出金待审批 + 当日佣金延迟
【IC】@xiaodong.wang
【Comms】@luchen.li
【Ops】@当班值班
【时间线】持续更新中

⏰ 下次同步：02:15
```

### Action 4 · 对外通报（按需）

- **内部老板**：仅 P0 才发，简短描述 + 预计恢复时间
- **业务方**：发飞书消息，安抚 + 进度
- **客户**：必要时发邮件 / 公告

模板：

```
尊敬的代理：

我们注意到 [简述现象]。我们的工程团队正在紧急处理。
预计 [时间] 前恢复。给您带来的不便，深表歉意。

如有疑问，请联系：[客服]
```

---

## 阶段 3 · 控制（"止血"优先 · 15-45 分钟）

### 核心原则：先止血，再追因

| 优先级 | 操作 | 例 |
|---|---|---|
| 1 | **隔离** | 隔离问题服务实例 / 限制问题用户 |
| 2 | **回滚** | 把最近的部署回滚（K8s rollout undo） |
| 3 | **降级** | 关闭非核心功能，保住主流程 |
| 4 | **限流** | 限制 QPS 避免雪崩 |
| 5 | **重启** | 实在没头绪时（带备份） |

### 决策 checklist

```
当前症状：xxx
已确认原因：xxx（如果还没确认就跳过）
可选方案：
  方案 A：xxx，影响 xxx，可逆性：xxx
  方案 B：xxx，影响 xxx，可逆性：xxx

IC 决策：方案 X
执行人：xxx
执行时间：xxx
```

### 操作记录规范

每个操作必须记录：
```
[02:18] @luchen.li 执行 kubectl rollout undo deployment/cpa-job-executor
       影响：恢复到 v1.2.3
       验证：观察 5 分钟，看 XxlJob 是否正常执行
```

---

## 阶段 4 · 恢复（验证 + 监控）

### Action 1 · 验证恢复

| 验证项 | 怎么验 |
|---|---|
| 业务监控 | Grafana 看核心指标恢复 |
| 业务功能 | 抽样测试关键流程 |
| 数据一致 | 抽查关键表（如 `tb_p_c_account_balance`） |
| 告警停止 | 飞书告警不再触发 |

### Action 2 · 持续观察

声明"故障恢复"前至少观察 30 分钟。

### Action 3 · 对外通报恢复

```
✅ P0 故障已恢复

【时长】02:00 - 02:35（35 分钟）
【根因】xxx（一句话）
【恢复方式】回滚到 v1.2.3
【后续】24h 内复盘报告
【感谢】@相关人 通力配合
```

### Action 4 · 解散战时群（24h 后）

```
本群将在 24 小时后归档。
复盘报告：[飞书链接]
如有补充，请回复本消息。
```

## 阶段 5 · 复盘（24h 内）

### 标准复盘报告模板

```markdown
# 【故障复盘】P0 · [标题]

## 1. 基本信息

| 字段 | 内容 |
|---|---|
| 等级 | P0 |
| 时间 | 2026-05-31 02:00 - 02:35 |
| 时长 | 35 分钟 |
| 影响范围 | 1235 个代理出金延迟，$xxx 资金延迟到账 |
| IC | @xiaodong.wang |
| 复盘日期 | 2026-06-01 |
| 复盘负责人 | @xiaodong.wang |

## 2. 时间线

| 时间 | 事件 |
|---|---|
| 02:00 | XxlJob 监控告警触发 |
| 02:02 | 当班值班 acknowledge |
| 02:05 | 升级为 P0，IC 接手，建战时群 |
| 02:10 | 初步定位：cpa-job-executor v1.2.4 部署后异常 |
| 02:18 | 执行回滚到 v1.2.3 |
| 02:25 | XxlJob 恢复执行 |
| 02:30 | 业务监控恢复 |
| 02:35 | 声明恢复，持续观察 30 分钟 |

## 3. 根因分析（5 Whys）

Why 1：为什么佣金计算停止？
  → bonusBatchJob 抛 NullPointerException

Why 2：为什么 NPE？
  → 新版本中 `clientSummary.getRule()` 返回 null

Why 3：为什么 getRule() 返回 null？
  → 重构时漏了 loadRule() 调用

Why 4：为什么漏了 loadRule？
  → 单测 mock 了 rule，没覆盖到这个分支

Why 5：为什么单测没覆盖？
  → 没有"集成测试"环节，纯单测覆盖度不够

→ **根因**：测试体系缺失"集成测试"环节

## 4. 影响范围（量化）

- 时长：35 分钟
- 影响代理：1235 人
- 影响金额：$15,400 佣金延迟入账
- 用户感知：低（凌晨 + 自动恢复）
- 客户投诉：0
- 媒体曝光：0

## 5. 处置评价

✅ 做得好：
  - 5 分钟内升级 P0，没有犹豫
  - 回滚操作果断、可逆
  - 沟通及时

⚠️ 待改进：
  - 排查阶段花了 13 分钟，可优化
  - 战时群拉得有点晚

## 6. 改进项（Action Items）

| 改进项 | 负责人 | 截止时间 | 状态 |
|---|---|---|---|
| 引入集成测试框架（用 api-test-automation） | @luchen.li | 2026-06-30 | 进行中 |
| 关键 Service 加 100% 分支覆盖率 | @xiaodong.wang | 2026-06-15 | 进行中 |
| 部署前必须跑集成测试 | @sre-lead | 2026-06-30 | 待启动 |
| 告警增加"任务连续失败 3 次"规则 | @当班值班 | 2026-06-10 | 待启动 |
| 战时群启动 SOP 文档化 | @xiaodong.wang | 2026-06-07 | 待启动 |

## 7. 预防同类问题

- 测试体系：引入集成测试 → 已立项
- 部署流程：增加自动化测试关卡 → 已立项
- 监控告警：增加 Job 连续失败告警 → 已立项

## 8. 后续跟踪

- 改进项进度：每周一同步
- 同类故障复发：将归类为重大问题
```

### 复盘会议

P0 必须开复盘会：
- 时长：≤ 90 分钟
- 参会：IC + 战时群核心成员 + Tech Director
- 输出：复盘文档 + Action Items（必须有负责人 + 截止时间）

---

## 反例：常见的错误响应

| 错误 | 后果 | 正解 |
|---|---|---|
| 没人当 IC | 多人各自操作，进一步搞乱 | 必须任命，越早越好 |
| 边查边操作 | 操作还没生效就忘了在做什么 | 一次一个操作，记录后再下一个 |
| 不告诉业务方 | 业务方乱猜，发奇怪通知 | 主动通报，哪怕"还在排查" |
| 跳过复盘 | 同样问题反复 | 强制 24h 内复盘 |
| 复盘甩锅 | 团队信任崩溃 | 复盘只谈系统问题，不指责个人 |
| 改进项不跟踪 | 改进项空头支票 | 周会跟踪进度 |
