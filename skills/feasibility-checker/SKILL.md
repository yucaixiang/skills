# feasibility-checker · 技术可行性自检

> 让产品在交付 PRD 前就能自助判断"这事儿能不能做"，少找研发 3 次。

---

## When to Activate

- 用户说"评估一下 xx 需求的技术可行性"
- 用户说"这个需求有没有技术风险"
- 用户写完 PRD 草稿想自检
- 研发 review PRD 时快速判断改动量
- 产品需求评审前的预审

---

## 6 维度评估法

```
┌────────────────────────────────────────────────────────────────┐
│  1. 架构契合度    需求是否符合现有架构？是否破坏分层？        │
│  2. 数据可用性    所需数据是否已存在？是否需要新表/字段？     │
│  3. 性能可达性    性能要求是否在现有技术栈承受范围？           │
│  4. 安全合规性    是否触及监管、隐私、权限红线？               │
│  5. 外部依赖      是否依赖外部系统/团队？依赖是否稳定？        │
│  6. 工期合理性    预估工作量是否符合预期周期？                 │
└────────────────────────────────────────────────────────────────┘
```

每个维度给出：
- 🟢 **绿灯**：直接可做
- 🟡 **黄灯**：可做但有约束 / 需 trade-off
- 🔴 **红灯**：当前架构做不了 / 需要重大改动

---

## 维度 1 · 架构契合度

### 检查点

| 检查项 | 红线 |
|---|---|
| 是否跨业务域调用？ | hytech-cpa 严禁跨域，发现即红灯 |
| 是否破坏 4 层分层？ | Controller 写业务 / business 访问别业务库 → 红灯 |
| 是否需要新业务域？ | 4 个领域之外的需求 → 黄灯（架构师评审） |
| 是否需要新模块？ | 新增 module 可行但增加复杂度 → 黄灯 |

### 实操速判

**绿灯示例**：
- "代理出金页加余额展示" → 在 client 域 business 层加接口即可
- "新增一种佣金规则" → 实现 BonusCalculator 接口即可，无侵入

**黄灯示例**：
- "运营同事在 admin 后台直接看代理的 client 端登录历史" → 跨域读，需走 platform-api
- "实时推送告警到代理移动端 APP" → 需引入 WebSocket / 推送通道

**红灯示例**：
- "在 admin 后台直接执行代理端业务" → 严重跨域，红线
- "让 backend 层直接调外部 API" → 违反"backend 只做本业务数据"

## 维度 2 · 数据可用性

### 检查点

| 检查项 | 信号 |
|---|---|
| 所需数据已存在的表/字段？ | 🟢 直接可用 |
| 需要新加字段？ | 🟡 涉及 DDL + Convert / DTO 改造 |
| 需要新建表？ | 🟡 涉及 DBA 流程 + 数据迁移考虑 |
| 数据需要从外部系统同步？ | 🟡 需评估同步频率 / 一致性 |
| 数据涉及多品牌？ | 🟡 必须明确品牌隔离方案 |
| 历史数据需要回填？ | 🟡 需评估回填脚本 + 时长 |
| 数据来自不存在的源系统？ | 🔴 需先建源系统 |

### 实操速判

提需求时主动给出"数据 → 字段 → 表 → 来源"映射。

例：
> "在出金页显示可用余额"
>
> - 数据：可用余额 / 锁定余额 / 货币
> - 字段：`availableBalance` / `lockedBalance` / `currency`
> - 表：`tb_p_c_account_balance`
> - 来源：本系统现有 → 🟢 数据可用

## 维度 3 · 性能可达性

### 关键指标速查（基于 hytech-cpa）

| 场景 | 现有能力 |
|---|---|
| 单接口 P99 | 通常 < 200ms（简单查询）/ < 1s（复杂报表）|
| 单实例 QPS | ~ 500 |
| Redis 单 key 读写 | < 5ms |
| Kafka 端到端延迟 | < 100ms |
| MySQL 单表写入 | ~ 5000 tps |
| 定时任务批量 | 10w 条 < 5 分钟 |
| Feign 跨域调用 | + 50-100ms |

### 检查点

| 检查项 | 信号 |
|---|---|
| 性能要求在现有能力范围 | 🟢 |
| 需要新增缓存优化 | 🟡 引入 Redis 缓存层 |
| 需要异步化 | 🟡 引入 Kafka |
| 需要读写分离 | 🟡 走 `cpa-client-read-service` |
| 性能要求远超现有能力 | 🔴 需重新架构 |
| 实时性要求 < 50ms 但走远程调用 | 🔴 物理不可达 |

### 反例

> "出金审批通过后实时通知代理（要求 < 100ms）" → 🔴
> 当前链路：审批 → BPM → Kafka → consumer → 通知服务，端到端 ~ 500ms
> 解法：要么调整为"准实时（< 5s）"，要么改架构（同步推送）

## 维度 4 · 安全合规性

### 红线场景

| 场景 | 信号 |
|---|---|
| 涉及客户身份证 / 银行卡明文存储 | 🔴 必须加密 |
| 涉及跨境数据传输 | 🟡 走合规通道（如 AWS Bedrock） |
| 涉及监管报送字段 | 🟡 需合规评审 |
| 新增对外开放接口 | 🟡 需鉴权 + 限流 + 审计日志 |
| 用户隐私数据日志输出 | 🔴 必须脱敏 |
| 影响代理资金安全 | 🔴 必须 BPM 审批 + 双人复核 |

### 检查点

- [ ] 涉及的字段是否包含 PII？
- [ ] 涉及的接口是否需要鉴权？
- [ ] 涉及的操作是否需要审计日志？
- [ ] 涉及的功能是否触及监管要求？
- [ ] 是否需要合规负责人评审？

## 维度 5 · 外部依赖

### hytech-cpa 主要外部依赖清单

| 依赖 | 用途 | 稳定性 |
|---|---|---|
| DAP/User 服务 | 用户基础信息 | 🟢 稳定 |
| MT4/MT5 数据库 | 交易数据 | 🟢 稳定 |
| CRM 系统 | 销售关系 | 🟡 偶发延迟 |
| 飞书 | 告警 / 文档 | 🟢 稳定 |
| 支付网关 | 出金支付 | 🟡 受外部限制 |
| Cellxpert（历史） | 已淘汰 | - |

### 检查点

| 检查项 | 信号 |
|---|---|
| 依赖现有稳定系统 | 🟢 |
| 依赖跨团队接口（未沟通） | 🟡 需协调对方排期 |
| 依赖暂不存在的系统 | 🔴 阻塞 |
| 依赖外部第三方 API | 🟡 需考虑 SLA / 降级 |

## 维度 6 · 工期合理性

### 速估算法

| 改动类型 | 典型工期（含开发+测试） |
|---|---|
| 加一个 GET 查询接口 | 1-2 人日 |
| 加一个 POST 写接口 | 2-3 人日 |
| 加一个 Service 业务方法 | 1-2 人日 |
| 新增一个 BonusCalculator | 3-5 人日 |
| 新加一张表 | 2-3 人日（含 DBA） |
| 改一个 Entity 字段 | 0.5-1 人日（+ 关联改动） |
| 新增定时任务 | 1-2 人日 |
| 新增 Kafka 消费 | 2-3 人日 |
| 跨域新增 platform-api | 5-7 人日（双方协调） |
| 新加一个完整业务模块 | 15-25 人日 |
| 改造分层架构 | 30+ 人日（极少建议） |

### 检查点

- 需求拆成 P0 项，每项独立估算
- 加上联调 / 测试 / 灰度时间（通常 = 开发的 50%）
- 留 10-20% 缓冲

### 实操速判

> "支持代理出金页查可用余额"
> - REQ-1（顶部展示）：2 人日
> - REQ-2（锁定余额显示）：1 人日
> - REQ-3（30s 自动刷新）：1 人日
> - REQ-4（输入超额提示）：1 人日
>
> 合计 5 人日 + 联调测试 3 人日 = **8 人日**
>
> 若 PRD 要求 3 天内交付 → 🔴 不合理
> 若 PRD 要求 2 周内交付 → 🟢 合理

## 反例：常见误判

| 产品估计 | 实际 | 教训 |
|---|---|---|
| "改一个字段而已" | 涉及 5 个 Convert + 3 个接口 + 1 张表 + 测试 → 5 人日 | 改 Entity 是连锁反应 |
| "复用现有接口就行" | 现有接口出参不含所需字段 → 改接口 → 影响调用方 | 复用 ≠ 零成本 |
| "性能要求差不多就行" | "差不多"= 没数字 → 上线踩坑 | 必须给具体 RT / QPS |
| "数据从 xx 系统取" | 对方接口未开放 → 阻塞 | 提前对齐数据源 |
