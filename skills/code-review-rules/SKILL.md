# 代码评审准则 (Code Review Rules)

> 评审不是挑刺，是**第二双眼睛**保障业务正确、技术健康、团队水位齐平。
> 本 Skill 是公司 PR 评审的统一标准，融合《阿里巴巴 Java 开发手册》+ hytech-cpa 真实评审实践 + 业界共识。

---

## When to Activate

- 在 GitLab / GitHub PR 上评审他人代码
- 自己提 PR 前做 Self-Review
- AI 自动评审（CI 钩子触发）
- 任何"这个改动应该这样改吗？"的判断

---

## 评审三视角 + 严重度分级

### 三视角

| 视角 | 关注点 | 检查重点 |
|---|---|---|
| **🎯 业务视角** | 改动是否真的解决了业务问题？ | 需求一致性、业务正确性、边界场景 |
| **🛡️ 技术视角** | 改动是否符合工程标准？ | 分层、命名、异常、并发、SQL、安全 |
| **🔍 可维护视角** | 改动是否对后续可读、可改？ | 复杂度、注释、测试、命名表达力 |

### 严重度分级

| 标记 | 严重度 | Reviewer 操作 | 例 |
|---|---|---|---|
| 🔴 **[Blocker]** | 阻断合并 | 必须修才能合并 | 漏需求、逻辑错误、安全漏洞、破坏性变更 |
| 🟠 **[Major]** | 强烈建议修 | 建议本次 PR 修复 | 性能隐患、可读性差、缺少关键测试 |
| 🟡 **[Minor]** | 改进建议 | 可单独 PR 修 | 命名优化、注释补充、格式 |
| 🟢 **[Praise]** | 表扬好实践 | 鼓励 | 优雅设计、好测试、好命名 |
| ❓ **[Question]** | 提问澄清 | 等回复 | 没看懂意图、希望解释 |
| 💡 **[Suggestion]** | 个人建议 | 作者可选 | 替代方案 |

## 评审标准动作（每次 PR 必走）

### Step 1 · 先读 PR 描述（不读代码）

| 检查项 | 通过标准 |
|---|---|
| ✅ 背景（Why） | 说清楚为什么改 |
| ✅ 改动（What） | 列出主要改动点 |
| ✅ 测试 | 自测方案 + 单测 |
| ✅ 风险 | 影响范围 + 回滚方案 |
| ✅ 关联需求 | Refs: PROJ-XXXX |

❌ 描述缺失或敷衍 → 提交 `[Blocker] PR 描述不完整，请补充`，**等补全再评审**。

### Step 2 · 看改动文件清单（俯瞰）

判断：
- 是否符合本 PR 的"主题"？（防夹带"顺手优化"）
- 涉及哪些模块？需要拉对应 Owner 一起 Review？
- 文件数量是否合理？（>30 个文件的 PR 建议要求拆分）

### Step 3 · 业务视角检查（最重要）

> **这是 Reviewer 的核心价值：技术规范有 AI / Lint 工具兜底，业务正确性只能靠人。**

#### 业务正确性 Checklist

- [ ] 改动**是否完成了需求描述的所有点**？（漏点 = Blocker）
- [ ] 边界场景是否覆盖？（空输入 / 极大值 / 极小值 / 并发 / 重复调用）
- [ ] 异常分支是否合理？（失败时数据是否一致？是否会重复发钱？）
- [ ] 与现有业务流程是否冲突？（如：改了佣金计算，影响分润吗？影响结算吗？）
- [ ] 数据是否会乱？（如：改了关系 path 字段，旧数据如何兼容？）
- [ ] 是否影响其他模块？（如：改了 RuleEntity，所有 Calculator 都跑通了吗？）
- [ ] 是否需要数据迁移？是否有迁移脚本？

#### 业务反例库（评审中常踩的坑）

| 反例 | 后果 | 评审动作 |
|---|---|---|
| 改了 FTD 计算但没改 Country 计算 | 业务一致性破坏 | `[Blocker] Country 模式下同样需要这个修复，请补充` |
| 加了新枚举但没更新枚举校验 | 漏校验 | `[Blocker] 新枚举值需在 XxxValidator 中添加` |
| 加了新字段但没改 MapStruct | 字段不同步 | `[Major] ClientSummaryConvert 缺少新字段映射` |
| 改了规则但没考虑 ruleSnapshot | 历史协议失效 | `[Blocker] 已签协议的快照会失效，需补迁移 / 兜底` |
| 加了写库操作但没在事务里 | 数据不一致 | `[Blocker] 这段写库需要包在 @Transactional 中` |
| 余额变动没写流水 | ledger 缺失 | `[Blocker] 余额变动必须同时写 AccountBalanceRecord` |
| 关系变更没更新 path 字段 | 分润算错 | `[Blocker] CpaAccountPathEntity 需要同步更新` |
| 改了接口签名没改调用方 | 编译炸 | `[Blocker] XxxApi 是跨服务接口，请同步更新调用方` |

### Step 4 · 需求一致性核验

- [ ] 对照 PRD / Jira ticket，逐条核对功能点
- [ ] 文案 / 错误码 / 字段含义与产品定义一致？
- [ ] 涉及的接口是否符合接口文档？需要更新文档吗？

⚠️ **特别警惕"看似实现，实际没做"**：
- "支持批量导入" → 真的支持多文件？还是只能一个？
- "校验失败给出提示" → 提示是哪种级别？文案是什么？
- "支持取消" → 取消后状态如何？余额如何处理？

### Step 5 · 技术规范检查

参考 `dev-standards` Skill 的 16 条规则，重点检查：

#### P0 红线（必查）

- [ ] 分层是否正确？（Controller 没写业务、business 没碰其他业务库、backend 没返 Entity）
- [ ] URL 前缀是否符合（`/bsn` `/bck`）？
- [ ] 类名 / 方法名 / 字段名是否合规？
- [ ] 异常用 BizException + ResponseEnum？没有裸 catch 吞异常？
- [ ] SQL 用预编译？无 `SELECT *`？大表 UPDATE/DELETE 有 LIMIT？
- [ ] Redis Key / Kafka Topic 用常量？
- [ ] 没有硬编码密钥 / 密码？
- [ ] 日志用占位符？异常带堆栈？没有敏感信息？
- [ ] 共享变量线程安全？分布式锁正确使用？

#### P1 黄线（重点关注）

- [ ] 方法 ≤ 80 行？类 ≤ 800 行？
- [ ] 依赖注入用 @RequiredArgsConstructor + final？
- [ ] 异常的 finally 是否只放资源释放？
- [ ] 集合判空用 CollectionUtils？
- [ ] equals 反向调用？
- [ ] 包装类比较用 equals？
- [ ] 包结构正确（controller / service / mapper / model 各司其职）？

### Step 6 · 可维护性检查

#### 代码可读性

- [ ] 命名表达力够强？（一眼能看懂干什么）
- [ ] 复杂逻辑有注释解释 WHY？（不是 WHAT）
- [ ] 魔数有常量替代？
- [ ] 长方法已拆分？嵌套层级 ≤ 3 层？

#### 单测覆盖

- [ ] 核心逻辑有单测？（特别是 Calculator / Service / 状态机）
- [ ] 测试方法命名 `should_xxx_when_xxx`？
- [ ] 边界 / 异常分支也有测？
- [ ] 测试可重复运行？无外部依赖？

#### 设计合理性

- [ ] 抽象是否合理？（过度抽象 ≠ 优雅）
- [ ] 是否破坏了现有的扩展点？（如：BonusCalculator 加 if-else 而不是新增策略实现）
- [ ] 命名 / 文件位置符合既有约定？

### Step 7 · 性能与安全（视改动而定）

#### 性能

- [ ] 循环里有 DB / Feign / Redis 调用？→ 批量化
- [ ] 大查询有分页？走只读服务？
- [ ] 缓存使用合理？（缓存击穿 / 雪崩防护）
- [ ] 异步执行场景是否有线程池命名 + 拒绝策略？

#### 安全

- [ ] 接口有鉴权 + 限流？
- [ ] 用户输入有校验（@Valid）？
- [ ] 敏感字段日志脱敏？
- [ ] 文件上传 / 下载有路径校验？
- [ ] SQL / Redis / Shell 注入风险？

## 评审写作风格

### 👍 好评论的样子

```
[Blocker] 业务逻辑错误
这里 line 142：
  if (ftdAmount.compareTo(threshold) >= 0)
但 PRD 第 3 节明确要求"严格大于 threshold 才合格"。
建议改为 > 0。

参考：ClientSummaryDto 现有的 isStrictlyQualified() 实现。
```

```
[Major] 性能
这里循环里调了 Feign，n=1000 时会触发 1000 次远程调用。
建议批量：参考 PlatformJobExternalApi.queryUserInfoList(List<Integer>)
```

```
[Question] 这个 RedissonLock 的 timeout=3s 是不是有点短？
我看 hytech-cpa/04-tech-stack.md 推荐 30s。
是有特殊原因吗？
```

```
[Praise] 这个 ApproveWorkFinishedHandler 的回调设计很赞！
未来扩展新的业务流程只需要实现 SPI 即可，不需要改 BPM 核心。
```

### 👎 坏评论的样子

```
❌ "这段代码不好"          ← 没说哪里不好
❌ "改一下"                 ← 没说怎么改
❌ "你怎么这么写"           ← 攻击人
❌ "我建议重构整个 Service" ← 范围扩大
❌ "这种写法 LowB"           ← 不专业
```

## 业务正确性评审深挖技巧

### 技巧 1 · 反推需求

读懂代码后**反向写一句话需求**："这段代码实现了 XX"。然后跟 PRD 对一下 —— 一致才合格。

### 技巧 2 · 跑一遍极端 case

- 入参全为 null
- 入参超长字符串 / 极大数
- 并发 100 人同时调
- 网络突然断 / DB 重启
- 用户连点 5 次提交

每个 case 想：会怎样？数据会乱吗？

### 技巧 3 · 寻找"漏的另一半"

| 加了 X | 是否需要补 Y？ |
|---|---|
| 加了新枚举 | 枚举校验 / Switch 分支 / DB 字段长度 |
| 加了写表 | 流水 / 索引 / 监控 |
| 加了缓存 | TTL / 缓存清除 / 击穿防护 |
| 改了 API | 调用方 / API 文档 / 兼容性 |
| 改了 Entity | MapStruct / DTO / Validator / SQL |
| 加了状态 | 状态机 / 状态校验 / 回滚 |
| 加了配置 | 默认值 / 配置中心 / 不同环境 |

### 技巧 4 · 查"看似没改但被影响的地方"

- 共享 Service 改了实现 → 它的所有调用方都受影响
- Entity 加了字段 → 所有相关 Mapper XML 是否要改？
- 枚举改了值 → 数据库已存数据怎么办？

## PR 审批流程（公司规范）

### 标准流程

```
作者提 PR → 自检 dev-standards → CI 全绿 → 申请 Review
       ↓
Reviewer 评论（按 Blocker / Major / Minor 分级）
       ↓
作者回复并修改
       ↓
Reviewer 确认无 Blocker → Approve
       ↓
合并到目标分支
```

### 审批人要求

| 改动类型 | 必须 Reviewer |
|---|---|
| 常规业务 | ≥ 1 名研发同事 |
| 核心业务（佣金计算 / 结算 / 审批 / 用户同步） | Tech Lead 必须 +1 |
| 跨域接口（platform-api） | 调用方域的 Owner +1 |
| 数据库 DDL | DBA +1 |
| 安全相关（鉴权 / 加解密） | 安全负责人 +1 |

### 合并条件

- [ ] 所有 Blocker 已修复
- [ ] 所有 Major 已修复或已说明
- [ ] CI 全绿（编译 / 单测 / 静态扫描）
- [ ] 至少 1 名审批人 Approve
- [ ] 涉及合规：合规负责人 +1

## Self-Review Checklist（作者提 PR 前必做）

> 提 PR 前自己当一回 Reviewer，能省 80% 反复评论。

```markdown
### 业务层
- [ ] 已实现 PRD 的全部功能点
- [ ] 已覆盖边界场景（空 / 极值 / 并发 / 重复）
- [ ] 失败回滚 / 重试 / 兜底已考虑
- [ ] 不影响其他业务（已查 import / 调用方）

### 技术层
- [ ] 已对照 dev-standards 的 P0 红线 16 条
- [ ] 没有夹带"顺手优化"
- [ ] 关键流程有日志（含业务标识）
- [ ] 关键异常有告警（larkCommMessagePusher）

### 测试层
- [ ] 单测已写，覆盖主要分支
- [ ] 本地接口验证通过
- [ ] 联调（如涉及）已通过

### 文档层
- [ ] PR 描述完整（背景 / 改动 / 测试 / 风险）
- [ ] 接口变更已更新文档（Knife4j 注解）
- [ ] 重要决策有 commit message 说明
```

## AI 评审增强（SkillForge 集成）

SkillForge 平台支持 AI 自动跑 Code Review。AI 评审会：

1. **结合项目知识 Skill 评审业务正确性**
   - 调 `hytech-cpa` Skill 理解业务上下文
   - 对照 PRD 检查需求覆盖度

2. **机械化检查技术规范**
   - 16 条 P0 红线（参考 `dev-standards`）
   - 命名 / 异常 / 日志 / SQL 模式扫描

3. **生成结构化评审报告**
   - 按 Blocker / Major / Minor 分级
   - 每条评论带文件位置 + 改动建议
   - 自动 @ 责任人（飞书告警链路）

4. **配合人工**
   - AI 评审是"地毯式扫描"
   - 人工评审是"业务深度判断"
   - 二者互补，不互相替代

## 反例：踩过的坑

> 这些是真实评审中出现过的问题，作为反例警示。

### 案例 1 · 漏需求

**改动**：实现 PRD"代理可以撤回出金申请"
**漏掉**：撤回后未释放锁定余额，导致代理钱"卡在中间"
**评审应说**：`[Blocker] 撤回时需调用 balanceService.releaseLocked()，否则锁定余额无法释放`

### 案例 2 · 业务边界

**改动**：新增"FTD 阶梯支持 $0-$100 区间"
**漏掉**：负数金额（误操作）会落入此区间
**评审应说**：`[Blocker] fromAmount 应有最小值 > 0 校验，避免误退款触发`

### 案例 3 · 跨模块影响

**改动**：在 `CpaAccountEntity` 加 `region` 字段
**漏掉**：未更新 `CpaAccountConvert`，跨服务调用拿不到该字段
**评审应说**：`[Major] CpaAccountConvert 需同步加 region 字段映射`

### 案例 4 · 并发陷阱

**改动**：余额变动加 RedissonLock，按 `account` 维度
**漏掉**：锁的 timeout=3s，高并发下大量重试
**评审应说**：`[Major] 余额变动通常涉及外部支付网关，建议 timeout >= 30s`

### 案例 5 · 性能反例

**改动**：批量更新 100 个代理状态，循环里调 Feign
**漏掉**：n=1000 时 100 倍 RT
**评审应说**：`[Blocker] 改用批量接口 cpaAccountInternalApi.batchUpdate(List)`

### 案例 6 · 安全漏洞

**改动**：根据用户传入的 fileName 下载文件
**漏掉**：未做路径穿越校验（`../../etc/passwd`）
**评审应说**：`[Blocker] fileName 需做白名单校验，禁止 .. 和绝对路径`

## 评审文化

### 我们的信念

- **代码 belongs to 团队**，不是某个人
- **每个评论都是学习机会**，作者和 Reviewer 都在成长
- **业务对了，再谈技术；技术对了，再谈风格**
- **快和好不矛盾**：好 PR + 好评审 = 综合最快

### 红线

- ❌ 不在评论里攻击人
- ❌ 不发只说"改一下"的评论（要给出方向）
- ❌ 不在 Review 里夹带"私货"（个人审美偏好）
- ❌ 不绕过 Review 直接合（仅限 hotfix，且事后补审）

### Reviewer 守则

- ✅ 24 小时内首次回复（不一定 Approve，至少表态）
- ✅ 大 PR 允许"分批 Review"（先大方向，再细节）
- ✅ 不懂的地方主动用 `[Question]` 提问，别装懂

### 作者守则

- ✅ Reviewer 评论积极回复，不抗辩
- ✅ 修复后再申请下一轮 Review
- ✅ 反复纠正同一类问题 → 自己整理 Checklist 防止再犯
